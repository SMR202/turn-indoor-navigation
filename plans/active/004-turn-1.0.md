# Plan 004: TURN 1.0, finished except the beacons

Status: ACTIVE (2026-11-06). Supersedes the "next" sections of [Plan 002](002-turn-masterplan.md) and [Plan 003](003-product-platform.md) where they conflict. Goal set by the owner: every part of the product is complete and shippable, so the only remaining step is mounting the ordered Minew E7 Plus beacons and running the verification walk. Rules as before: tick `[x]` only with evidence, never claim venue accuracy from simulation.

## 1. Where we are (FACT, 2026-11-06)

- **TURN app** (`apps/navigator`, Expo SDK 57, iPhone and Android): venue list, indoor map (custom SVG renderer), search, place cards, routes with named turns, demo walk, step-by-step, live guidance with a particle-filter blue dot, beacon setup and beacon test screens, "Not here?" corrections, QR location codes. Live walks at home reached three rooms (2026-10-28 recording).
- **TURN Studio** (`apps/console`): venues, GeoJSON map import with validation, places, beacon site suggestions, publishing with versions and QR codes, anonymous analytics, team, TURN Ops.
- **Server** (`apps/api`, Hono + SQLite): venues, versions, beacon layouts, beacon tests, location feedback; LAN-only private venues.
- **TURN-Mapper** (Zaki's module): 14 FAST floors exported in our venue format, loaded as 14 separate venues.
- **Positioning**: step detection, map-constrained particle filter, nearest-beacon room zones, honest display (accuracy circle, confirm-before-jump).

## 2. Problems seen in testing

1. **The dot went the wrong way at university** (user report, FAST). Diagnosis below (§4).
2. **The map glitches**: zooming stutters, taps are missed or land on the wrong thing, little feedback. Cause: the map is SVG redrawn by React plus Reanimated layers; every camera change re-renders large paths on the JS thread, and pan and tap gestures compete.
3. **The map looks flat and never turns with you**: no heading-up mode, no 3D, the dot is not kept centred while navigating.
4. **A campus is 14 venues** instead of one campus with buildings and floors.
5. **Every phone is treated the same**: signal strength and step length differ per model.
6. **No way to plan or verify beacons before buying them**: the beacon planner guesses sites but cannot say what accuracy a layout will give.

## 3. What "finished" means

Finished = a new venue can go from floor-plan PDF to a working navigation app without a developer, and a visitor can open the app and be guided reliably. Concretely:

| Journey                                               | Done when                                                                                                                                                                                                                                                                                                                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Venue onboarding** (staff, Studio)                  | Import TURN-Mapper output for a whole building or campus in one step; review it over the source plan; fix names, places and doors by hand; align the map to north on a satellite view; publish.                                                                                                                                                               |
| **Beacon programme** (staff, Studio + app Setup mode) | Studio proposes the fewest beacons for a target accuracy and shows the predicted accuracy map from simulation; prints an install sheet with numbered sites and stickers; the installer app walks the installer to each site, identifies the beacon in hand and verifies its signal; a verification walk with checkpoints produces a measured accuracy report. |
| **Visitor** (app)                                     | Opens the venue (list, QR code or link), searches, sees a 3D map that turns with them, starts guidance; the dot stays centred and moves smoothly; turns are announced by voice and haptics; leaving the route is noticed and a new route is offered; floor changes are guided; arrival is confirmed; uncertain positions are shown as uncertain.              |
| **Every phone**                                       | The app knows the phone model's signal offset and stride defaults, learns this phone's own values from normal use, and shares learned model values with the venue server.                                                                                                                                                                                     |
| **Operations** (Studio)                               | Beacon health from visitors' phones (last heard, signal trend, likely battery issues), accuracy dashboard per floor and phone model, usage analytics without personal data.                                                                                                                                                                                   |

What remains for beacon day (cannot be done without hardware): mount beacons, run the verification walk, record measured accuracy.

## 4. Diagnosis: the dot going the wrong way (EXPERIMENT RESULT from code reading)

- The map is **not mirrored**: TURN-Mapper flips y from image coordinates into x-right-y-up (`positioning_export.py`), and our renderer flips it back for the screen (`VenueMap.tsx`, `Y = oy - (y - cam.y) * s`). Room order on C-F4 matches the export.
- Both phones give an **absolute compass yaw** (Android rotation vector, iOS `xMagneticNorthZVertical`).
- What is missing is the **map's north**: the app only knows a venue's north offset after this phone has learned it on an earlier walk (`north-<venue>-<platform>` in local storage). On a new venue such as the FAST floors it falls back to "face along the blue line". If the walker faces any other way, the whole track is rotated; facing the opposite way makes the dot run backwards, and a straight corridor gives the filter nothing to notice it by.
- The map also never rotates to the walker's view, so the plan can look "opposite" to what they see.

Fix (Wave 1): every venue gets a map bearing (Studio alignment, or learned from staff walks and stored on the server, not per phone); starts use compass + bearing (σ about 35°, wider when the magnetic field looks disturbed); the map rotates heading-up while navigating; the filter keeps a 180° alternative hypothesis for the first metres; a one-time "Does the map match what you see?" check.

## 8. Mapping module (TURN-Mapper) recommendations for Zaki

Read from `ZakiNabeel/Turn-Mapper` at `abcc809` (2026-10-28).

- **North and georeference**: detect the north arrow on the plan and export the bearing; accept a site location. Today nothing carries orientation.
- **Scale confidence**: export the scale method and an uncertainty (already noted as "estimate"); flag floors where door widths disagree.
- **Unreachable destinations**: seven floors drop 1–2 destinations; export them with a `reachable: false` flag so Studio can show and fix them instead of losing them.
- **Building packages**: our import should take `A/`, `B/`, `C/` packages directly (floors joined by matched stairs and lifts).
- **Stable IDs**: keep room and place IDs stable across re-runs so corrections made in Studio survive a new export.

## 9. Risks

- Native builds: MapLibre and voice need a new app build on both phones (the iPhone sideload expired on about 4 Nov anyway).
- Indoor compass error can be 30–60° near steel; the filter must treat the compass as a hint.
- Simulated accuracy is a prediction for planning, not a result.
