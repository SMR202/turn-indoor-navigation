# Platform constraints
Verified against official platform documentation: 2026-09-12.
Target OS versions and device models: **UNKNOWN; team decision required.** Re-check
all version-dependent behavior when those are selected.

Claims are platform API constraints, not TURN device measurements. Every acquisition
adapter must feature-detect hardware, record permission/state transitions and expose
an explicit unavailable/denied/degraded status.

## Capability matrix

| Area | Android | iOS | TURN consequence |
|---|---|---|---|
| Wi-Fi scans | **FACT:** `getScanResults()` / `startScan()` access depends on OS/target-specific permissions; Android 10+ also requires Location services enabled. Android throttles scan requests: the documented Android 9+ limits are four scans per two minutes for each foreground app and one scan per 30 minutes collectively for background apps, with developer-option and OEM variability ([Android Wi-Fi scan overview](https://developer.android.com/develop/connectivity/wifi/wifi-scan), accessed 2026-09-12). | **FACT:** Apple states that iOS has no general-purpose Wi-Fi scanning/configuration API. Special-purpose APIs do not provide general nearby-AP fingerprints. `NEHotspotNetwork.fetchCurrent` returns only the current network and only under listed criteria plus the Wi-Fi Info entitlement ([TN3111](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview); [`fetchCurrent`](https://developer.apple.com/documentation/networkextension/nehotspotnetwork/fetchcurrent(completionhandler:)), accessed 2026-09-12). | **DECISION:** Wi-Fi is optional Android-only experimental input; never a cross-platform core dependency. Log scan request/result timestamps, age, failure and permission/location state. Do not represent connected-network lookup as scanning. |
| BLE scan | **FACT:** for apps targeting Android 12+, `BLUETOOTH_SCAN` is a runtime permission; `BLUETOOTH_CONNECT`/`ADVERTISE` apply to their operations. Older-target/device combinations can involve location permissions. The official BLE guide recommends stopping as soon as the desired device is found and setting a time limit because scanning is battery-intensive ([Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions); [BLE scan guide](https://developer.android.com/develop/connectivity/bluetooth/ble/find-ble-devices), accessed 2026-09-12). | **FACT:** Core Bluetooth supports central scanning, while background execution requires declared Bluetooth background modes and behaves differently from foreground use; declarations do not mean indefinite unrestricted execution ([Core Bluetooth background processing](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html); [`UIBackgroundModes`](https://developer.apple.com/documentation/bundleresources/information-property-list/uibackgroundmodes), accessed 2026-09-12). | **PROPOSED:** E001 starts foreground-only. Record authorization, Bluetooth state, advertisements, identifiers after privacy review, RSSI and monotonic receive time. Separately measure background behavior and battery before promising it. RSSI-to-distance remains an experiment. |
| Accelerometer / gyroscope / magnetic field | **FACT:** Android exposes raw and composite sensors; availability varies by device. `SensorEvent.timestamp` uses nanoseconds on the same time base as `SystemClock.elapsedRealtimeNanos()`. Android 12+ rate-limits some motion/position sensors unless a high-sampling permission is declared ([sensor overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_overview), accessed 2026-09-12). | **FACT:** Core Motion requires checking sensor availability; requested accelerometer frequency is capped by hardware. Apple documents acceleration in multiples of gravity and provides device-axis documentation ([raw accelerometer events](https://developer.apple.com/documentation/coremotion/getting-raw-accelerometer-events), accessed 2026-09-12). | **DECISION:** Store source monotonic timestamp, units, device frame, requested/observed rate, calibration/accuracy state and dropped/gapped samples. Convert units explicitly in replay. Never assume identical sampling or platform attitude conventions. |
| Heading | **FACT:** Android rotation-vector/orientation choices differ in magnetometer use and availability ([position sensor overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_position), accessed 2026-09-12). | **FACT:** Core Location heading availability must be queried; heading data exposes accuracy and magnetic/true values with platform conditions ([heading API](https://developer.apple.com/documentation/corelocation/cllocationmanager/heading), accessed 2026-09-12). | **EXPERIMENT:** compare gyro-only integration, platform attitude/heading and Fusion on identical logs. Define clockwise/counter-clockwise, north reference, radians/degrees and frame transforms. Treat poor/unavailable accuracy explicitly. |
| Pressure / floor | **FACT:** Android environment sensors are hardware-based and device manufacturers are not required to include them ([environment sensor overview](https://developer.android.com/develop/sensors-and-location/sensors/sensors_environment), accessed 2026-09-12). | **FACT:** `CMAltimeter` exposes relative altitude/pressure only where supported; availability must be checked ([CMAltimeter](https://developer.apple.com/documentation/coremotion/cmaltimeter), accessed 2026-09-12). | **DECISION:** pressure is optional evidence, not required input. Floor inference requires transition topology, venue evidence and a fallback/manual recovery path. |
| Location / initial pose | **FACT:** Android location permissions and background access are version/lifecycle sensitive ([location permissions](https://developer.android.com/develop/sensors-and-location/location/permissions), accessed 2026-09-12). | **FACT:** Core Location authorization differs for in-use and background access ([requesting authorization](https://developer.apple.com/documentation/corelocation/requesting-authorization-to-use-location-services), accessed 2026-09-12). | **PROPOSED:** first indoor experiment uses an explicit surveyed start pose. GNSS may assist outdoors/onboarding but is not assumed indoors. Ask only for permissions justified by the selected feature. |

## Lifecycle and validation constraints

- **FACT:** simulators and cloud replay cannot reproduce real sampling, radio policy,
  magnetic interference, carrying mode, thermal state or battery behavior.
- **PROPOSED:** maintain a device/OS/app-state capability matrix from actual E001
  sessions. A missing sensor, denied permission, disabled radio/location service,
  stale scan or background suspension must be observable rather than silently filled.
- **UNKNOWN:** minimum OS versions, background navigation promise, required sample
  rates, acceptable battery draw and iOS signing/build path.
- **DECISION:** no Android result is extrapolated to iOS. Acquisition, replay,
  localization, mapping/routing and UI remain separate boundaries.
